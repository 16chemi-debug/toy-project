# 기록 보관과 인증

## Decisions

- 기록은 사용자의 브라우저에만 보관합니다. 서버나 외부 서비스로 보내지 않습니다.
- 로그인이 없습니다. 앱을 연 사람이 곧 기록의 주인입니다.
- 앱 안에 잠금을 두지 않습니다. 기기를 함께 쓰는 사람이 건강 기록을 볼 수 있다는 것을
  알고 받아들인 선택이며, 기기 자체의 잠금에 기댑니다.
- 외부 계정, API 키, 자격증명을 쓰지 않습니다. 받아서 바로 실행하면 동작해야 합니다.

## Boundaries

- 이 결정은 기록이 어디에 남고 누가 접근하는지만 정합니다. 화면 구성과 기록 항목은
  각 작업 단위의 스펙이 정합니다.
- 기기 사이 동기화와 자녀의 원격 조회를 지원하지 않는다는 뜻도 함께 담고 있습니다.
- 잠금을 두지 않기로 한 것은 어머니가 매일 아침 넘어야 할 관문을 만들지 않기 위해서이기도
  합니다. 입력이 번거로워지면 종이 수첩으로 돌아가고, 그러면 제품 전체가 성립하지 않습니다.

## Why

이 저장소는 강의용 학습 템플릿입니다. 받아서 바로 도는 것이 코드 완결성보다 앞섭니다.
Supabase Cloud 프로젝트와 Google OAuth 자격증명은 세션마다 외부 계정 설정과 비밀 값
입력을 요구해서, 그 준비 자체가 실행을 막는 관문이 됩니다.

대가를 알고 택했습니다. 브라우저 저장은 캐시를 지우거나 기기를 바꾸면 3개월치가
사라지고, 사용자가 되살릴 방법이 없습니다. 이 앱의 가치는 "3개월치가 쌓여 있다"에
걸려 있으므로, 이 선택은 제품의 실패 경로를 열어둔 채 두는 것입니다. 그럼에도 자격증명
없이 도는 쪽을 앞세웠습니다.

## Reconsider when

- 기록을 실제로 잃는 일이 한 번이라도 생겼을 때
- 자녀의 원격 조회가 범위에 들어올 때
- 같은 기록을 여러 기기에서 봐야 할 때

"학습용이 아니라 실제로 쓰실 물건이 될 때"는 이미 지나간 조건입니다. 어머니가 실제로
쓰신다는 것을 알고 나서 이 결정을 다시 꺼내 살폈고, 되살릴 길(가져오기)을 지금 만들지
Supabase로 돌아갈지를 두고 그대로 두기로 정했습니다. 모르고 넘어간 것이 아닙니다.
남은 빈자리는 `docs/follow-ups/no-restore-path.md`에 있습니다.

## Still-rejected alternatives

- Supabase Cloud와 Google 로그인 — 유실 위험이 없고 원격 조회로 넓히기도 쉽지만,
  프로젝트 생성과 OAuth 자격증명 준비가 매번 필요해서 템플릿이 곧바로 돌지 못합니다.
  위 재검토 조건이 생기면 이 안으로 돌아갑니다.
- 서버의 JSON 파일 — 자격증명 없이 서버에 남길 수 있지만 브라우저 저장보다 구조가 늘고,
  배포 환경에 따라 유실 양상이 달라져 설명이 복잡해집니다.
